# Enviando código para uma segunda revisão

Quando modificações ou atualizações são sugeridas durante uma revisão, não é incomum que os desenvolvedores enviem seu código revisado para uma segunda revisão. Isso é para garantir que as alterações feitas sejam aceitáveis, eficientes e estejam de acordo com os padrões de codificação da equipe. Também oferece outra oportunidade para feedback dos pares, que é crucial para resolver quaisquer problemas remanescentes e acelerar o aprendizado da equipe. Para aproveitar ao máximo esse processo, lembre-se das dicas a seguir para ajudar a agilizar a segunda revisão e garantir que o código atualizado esteja no caminho certo:

- Aborde todos os comentários: certifique-se de compreender e incorporar todas as alterações sugeridas na primeira revisão antes de enviar o código atualizado.

- Mantenha o foco nas alterações: Envie apenas as alterações necessárias para a segunda revisão. Evite introduzir novos recursos ou modificações não relacionadas, pois isso pode prolongar o processo de revisão.

- Teste novamente seu código: depois de fazer revisões, certifique-se de que o código ainda esteja funcionando conforme planejado e que todos os testes ainda sejam aprovados. Isto economizará tempo na segunda revisão e inspirará confiança no código do ponto de vista do revisor.

- Forneça contexto: forneça um breve resumo ou resposta ao feedback do revisor, descrevendo as alterações feitas ou as razões por trás da manutenção de partes específicas do código como estão. Essa visão geral condensada tornará mais fácil para o revisor identificar as alterações sem a necessidade de reler o código inteiro.

- Marque uma reunião de acompanhamento: se necessário, agende uma reunião de acompanhamento com o revisor para abordar quaisquer preocupações ou partes pouco claras do feedback. Esta comunicação direta pode agilizar o processo de revisão e evitar mal-entendidos.

Ao incorporar essas práticas recomendadas ao enviar o código atualizado para uma segunda revisão, você agilizará efetivamente o processo e criará uma experiência positiva tanto para o desenvolvedor quanto para o revisor. Em última análise, isso levará a um código de maior qualidade e a um produto final com melhor funcionamento.
